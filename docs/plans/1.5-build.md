# 1.5 and the ad funnel — build plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **One task at a time, each on the owner's go** (one builder, its review, then the next; no parallel worktrees).

**Goal:** A Blinkist-style quiz on kiwiguide.app that ends with an account and a saved suggested trip the app opens, measured for Google Ads; then the 1.5 store build with Google Analytics for Firebase and a "Rate Kiwi Guide" row.

**Architecture:** The quiz is plain static files in `kiwiguide-site/public/plan/` (no build step, no SDKs), talking to Firebase Auth's REST api the way `public/reset/reset.js` already does, and saving through the engine api's existing `POST /v1/southislandguide/itineraries`. Its trips come from a `trips.json` exported from the app's `lib/itineraryTemplates.ts` and the live place list. The app side adds React Native Firebase analytics beside the web `firebase` SDK.

**Tech Stack:** Static HTML/CSS/JS on Cloudflare Workers assets, `node --test`; Firebase Identity Toolkit REST; Google tag (gtag.js) + Consent Mode v2; Expo SDK 58, `@react-native-firebase/app` + `analytics`, Jest.

**Spec:** [docs/plans/1.5-design.md](1.5-design.md) (owner approved 2026-11-20: "run the plan").

## Global Constraints

- Wording on every screen and in every email or page: Trip/Trips and "place"; never Itinerary, Plans or Location.
- Site: static files in `kiwiguide-site/public`; scripts only self-hosted (no inline script, no script CDNs); the CSP widens only by what a task names.
- Same Firebase project as the app (`southislandguide`); `kiwiguide.app` is an authorized domain. The Firebase web api key is public by design (the reset links already carry it).
- The api as it is: `POST https://api.blacksands.app/v1/southislandguide/itineraries` with `Authorization: Bearer <Firebase ID token>`; CORS `*`; 409 `date_overlap` when dates overlap a trip the user has.
- App Store id `6818057796`; provider token `pt=128674950`; the funnel's App Store links use `ct=quiz`.
- Seasons (southern): Summer Dec–Feb, Autumn Mar–May, Winter Jun–Aug, Spring Sep–Nov.
- 1.5 is a store build and a new runtime. No 1.5 change goes out as an OTA to 1.4 (`e8b1306b…`).
- 1.5 runtime (Task 9, with the analytics default-off Info.plist flag, before later native changes): `9a38b0142d7f20d50b65b05f3387eca13f0e772c` (Task 8: `6d4de70d88e3efd3132b2681d0aebc2dbb7c6fef`). It changes if any later task touches native config or deps. RNFB 27 needs `useFrameworks: "dynamic"`, not "static" (static fails pod install).
- No styling changes in the app before the 2.0 redesign, except the new Profile row in the existing row style.
- The owner sees designs first (Task 1); no critics unless the owner asks.
- Every deploy (`npx wrangler deploy`, `npm run deploy`), `wrangler secret put`, EAS build, submit and `eas update` is on the owner's separate go. Commit only what the task names; enginev1 is not a git repo.
- Firestore reads: a full place-list read from Firestore costs 559; the api's list is cached in KV (0 reads). Never loop list calls against a cold cache.

## Review Focus

1. **An existing account with a trip:** signing in on the site never replaces or deletes a trip; overlapping dates get a plain message and other dates to try. (Task 4, `saveErrorMessage(409)` test and the existing-account check.)
2. **No signal between "account made" and "trip saved":** retrying saves the trip with the same account, never a second sign-up. (Task 4, retry test.)
3. **Browser back mid-quiz:** goes to the previous question, not off the page; a reload keeps the answers. (Task 3, `stepFromHash` test and session-stored answers.)
4. **The current month picked after the 1st:** the trip starts tomorrow, never in the past. (Task 3, `startDateFor` test.)
5. **A visitor in the EU or UK:** consent stays denied, no Google cookies, and the quiz still works end to end. (Task 5, consent region test and a manual check.)

### Task 4b: Google sign-in on the site (owner, 2026-11-20: "add Google now")

**Files:**

**Approach (no third-party script, so the CSP stays self-hosted for scripts):** Google's OpenID Connect redirect. "Continue with Google" saves a random `state` and `nonce` in sessionStorage and goes to `https://accounts.google.com/o/oauth2/v2/auth?client_id=<web client>&redirect_uri=<origin>/plan/&response_type=id_token&scope=openid%20email%20profile&nonce=<nonce>&state=<state>&prompt=select_account`. Google returns to `/plan/#id_token=…&state=…`. The page checks `state`, removes the fragment from the address bar and history straight away, and calls Identity Toolkit `accounts:signInWithIdp` with `{ postBody: "id_token=<token>&providerId=google.com", requestUri: "<origin>/plan/", returnSecureToken: true, returnIdpCredential: true }`. The answer's `idToken` goes into the same in-memory session as an email sign-in, then the same save flow (Task 4: list, confirm-replace dialog, POST or PUT). The quiz's answers survive the round trip in sessionStorage (they already do).

**Interfaces:**
- Consumes: Task 4's `saveFlow`, session and screens.
- Produces (`account.js`): `GOOGLE_WEB_CLIENT_ID` (the app's `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`, public); `googleAuthUrl(origin, state, nonce): string`; `readGoogleReturn(hash: string): { idToken, state } | null`; `signInWithGoogle(fetchFn, idToken, requestUri): Promise<{ idToken, email, isNew }>`; `authErrorMessage` gains the idp codes.
