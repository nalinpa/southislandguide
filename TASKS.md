## Later

### 1.1 — drive times and multi-day
- The transit matrix is `{}` today, so every leg defaults to 1 slot (30 min). Generate it with a port of `rotorua-guide/scripts/generate-transit-matrix.js`.
- **`durationToSlots()` caps at 4 slots (2 hours).** Fine for Christchurch; wrong the moment places are hours apart — Queenstown → Christchurch is ~12 slots. Uncap it before 1.2.
- **Distance Matrix cost is N².** 53 places ≈ 1,400 pairs ≈ $7. The whole island is ~$1,000+ without regional clustering (exact pairs within a region, hub-to-hub between regions).
- **The matrix is per area, not island-wide** (decided 2026-10-13). Two levels: place-to-place times only between places in the same `area`, and one drive time for each pair of areas, which is what the drive block shows. So Christchurch place → Christchurch place reads the area's own matrix, and Christchurch place → Dunedin place reads the Christchurch–Dunedin time. This removes the N² problem above: the place matrices grow with the size of each area (about 1,250 pairs, roughly $6, for the 96 places live today, against about 3,900 for one matrix), and the area table is three pairs today, few enough to enter by hand. Real place-to-place times inside an area are for later; flat 30 minutes stands until then (owner, 2026-10-13). Known roughness: one time per pair of areas means north Christchurch → south Dunedin reads the same as south Christchurch → north Dunedin. Cheapest correction, needing no new fields: scale the area-to-area time by the straight-line distance between the two actual places over the straight-line distance between the two area centres (`distanceMeters`, each area given one centre point), then round to the half hour. If places well off the main road still read wrong (a peninsula, say), add one optional per-place number of extra minutes for those only. Still to settle when building: the lookup takes two site ids and has to know each one's area, so either the generated file carries a site → area map or the callers pass it in.
- Day grid is 8am–10pm (28 slots); a long drive can eat most of a day. Start by rendering it as one tall transit block and see if that's usable before building anything structural.
- **Driving time as a block in the day view** (added 2026-10-13). **Not** the existing transit connector: `ItineraryDetailView.tsx` already draws the shared kit's `TransitBlock` (dashed line, train icon, "Transit 30 min") in the gap between two places, and that is a different thing. What it is (owner, 2026-10-13, "more like" this): a drive shown as a full block on the timeline, like a place — a card reading "Drive to Dunedin", from and to, and the duration — taking up its real time in the day and placed automatically between places that are far apart. Not something the user adds or moves, so nothing new is stored in the trip. The planner already reserves the time (`forwardCascade` in `lib/utils/itineraryPhysics.ts` pushes the next place back by the transit slots), so this is mostly a new local block drawn in that reserved gap. Decided 2026-10-13: the block appears when the two places are in different areas — `Site.area`, the base town a place is visited from (`christchurch`, `timaru`, `dunedin`), one level below `region` — and the card names the area ("Drive to Dunedin"), not the place. Within an area the small connector stays. `area` is an id, so the card needs a display label for each one. Needs real drive times first: the generated matrix, uncapped, and for pairs the matrix lacks a straight-line estimate from `lib/utils/geoDistance.ts` rather than the flat 30 minutes (a fallback only: Queenstown to Milford is 70 km straight and 290 km by road). Check a day still works when one drive takes most of the 8am–10pm grid.
- **A trip view with the city or cities for each day** (added 2026-10-13). One row per day: date, town(s), and the drive between them. The town is the place's `area` (all 96 live places have one as of 2026-10-13: 46 `christchurch`, 35 `dunedin`, 15 `timaru`), the same field the drive block uses, so no town list or nearest-town lookup is needed. Decided 2026-10-13: the towns are derived, not chosen by the user: each area among the places already in that day, in visit order, so nothing new is stored in the trip. Not decided: where the view sits on the trip screen.

### 1.4 — Commerce
- **Every place in `assets/data/christchurch_places_all.json` has `premium: true`.** It was deliberately NOT written to Firestore: enginev1/api's locations route (`routes/locations.ts:85`) strips any `isPremium` doc to a teaser for callers without an unlock, and that check is **not** gated on the app having commerce configured — so for this app it would blank every description, or 503 the whole list. When IAP lands, choose the premium set deliberately; all-premium means nothing is free.
- Swap the two stubs for rotorua-guide's real files: `lib/hooks/useEntitlementGate.ts`, `lib/iap/PurchaseProvider.tsx`. See their `ponytail:` comments.
- Firestore rules: flip `locations` to deny client reads — only AFTER the api reads with the service account. Order is in the comment in `firestore.rules`.
